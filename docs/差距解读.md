# 差距解读：现在做法 vs 之前做法

> 本文对比「现在的新框架（mc-model-bench）」与「之前的单文件脚本 `kimi_k3_easyrouter_vs_mayi.py`」在测试方法与工程实现上的差距。
> 说明：之前的完整测试报告位于飞书文档（https://cheetah-mobile.feishu.cn/docx/Q8ktdpumtoCbZgxWVITcEoqonWb），沙箱环境无法直连飞书，因此本解读以之前提交的测试代码 `kimi_k3_easyrouter_vs_mayi.py`（即产出该报告的执行代码）为权威依据展开对比。

## 一、结论先行

| 维度 | 之前做法（单文件脚本） | 现在做法（mc-model-bench） |
|---|---|---|
| 渠道配置 | 硬编码在 `PLATFORMS` 字典里（api_key 明文） | 独立 `config/providers.json`，api_key 走环境变量 |
| 渠道数量 | 固定 2 个（EasyRouter vs Mayi） | 任意 N 个渠道，一行配置一个 |
| 测试用例 | 硬编码在代码里（5 组用例数组） | 独立 `test_cases/*.json` + 可从 HuggingFace 下载抽取 |
| 请求构造 | `openai` SDK（高层封装） | 原生 HTTP + 统一构造函数（完全可控、可比） |
| 变量控制 | 每次运行 prompt 一致，但无显式机制保证 | 长输入用「用例ID」种子确定性生成，prompt 全渠道逐字一致 |
| 性能指标 | TTFT / chunk数 / 生成速度(chunk/s) / 端到端 | TTFT / 内容TTFT / chunk 大小与间隔分布 / 速度(tok/s) / 端到端 / usage |
| 推理模型适配 | 有（reasoning_content、reasoning_tokens） | 有（reasoning_content、reasoning_tokens、content_ttft 分离） |
| 缓存机制 | 有（cached_tokens、前缀 cache） | 有（cached_tokens 采集；前缀 cache 见文末差距清单） |
| 质量/幻觉 | 有（数学/代码/指令/幻觉/一致性，人工看输出） | 有（GSM8K 精确判分 + TruthfulQA 命中判分，来自 HF） |
| 结果输出 | 控制台表格 + 可选单个 JSON | 原始 JSON（逐用例）+ 汇总 JSON + Markdown 对比表 + Excel 报告（带公式） |
| 可复现/可审计 | 弱（结果一次性打印，难以回溯） | 强（全量数据落盘，order.json 记录发送顺序与时间戳） |

## 二、之前的做法（kimi_k3_easyrouter_vs_mayi.py 复盘）

### 2.1 结构
- 单文件 928 行，10 个对比模块：`perf / tokens / compat / quality / longctx / fingerprint / hallucination / complex / consistency / cache`。
- 使用 `openai.OpenAI(base_url=..., api_key=...)` 客户端，`chat.completions.create(...)` 调用。

### 2.2 优点（值得保留，新框架已继承）
1. **覆盖推理模型**：`stream_call` 里分别采集 `delta.content` 与 `delta.reasoning_content`，TTFT 以「首个 token（内容或推理）」计，符合推理模型的评测习惯。
2. **覆盖缓存机制**：`prompt_tokens_details.cached_tokens` 命中检测 + 前缀 cache 对比，能发现「渠道 A 注水缓存 / 渠道 B 无缓存」这类服务差异。
3. **覆盖质量/幻觉**：数学推理、代码生成、指令遵循、虚构知识检测、同 prompt 一致性，贴近业务实际。
4. **温度兼容处理**：`TEMPERATURE_SUPPORTED = False`，对 kimi-k3 这类不支持 temperature 的模型不传该参数，避免大面积报错。

### 2.3 不足（新框架针对性改进）
1. **配置与用例耦合在代码里**：换渠道要改代码；api_key 明文入库有泄露风险。
2. **只有 2 个渠道**：无法扩展到「同一模型 × N 渠道」的横向对比。
3. **无统一变量控制机制**：长文本、性能 prompt 每次手写，跨渠道一致性靠人工保证。
4. **用例无法从外部数据源注入**：没有 HuggingFace 等基准数据下载/抽取能力，质量层用例是手工挑的 3 条。
5. **输出只有控制台 + 单 JSON**：没有逐用例原始数据落盘、没有 Markdown 对比表、没有带评分公式的 Excel 报告，结果不可回溯、不可批量汇总结论。
6. **速度口径不一致**：旧脚本用 `chunk/s`（chunk 数与网络分块强相关，不反映真实吞吐），新框架改为 `completion_tokens / 生成耗时`（tok/s），并保留 chunk 分布。
7. **chunk 分布缺失**：旧脚本只统计 chunk 数量，新框架记录每个 chunk 的到达时间与大小（min/avg/max/std + 逐条时间线），可定位「首字快但后续卡顿」这类问题。

## 三、现在的做法（mc-model-bench 框架）

见 `README.md` 与 `docs/代码解读.md`。核心变化点：

1. **配置外置**：`config/providers.json` 一行一个渠道，只换 `base_url / api_key / model`；api_key 用环境变量 `EASYROUTER_API_KEY` / `MAYI_API_KEY` 注入。
2. **统一请求构造**：`runner.build_request_body()` 一处生成所有渠道的请求体，共用 `shared_request_params`，长输入填充文本用 `stable_seed(用例ID)` 生成，保证全渠道 prompt 逐字一致。
3. **用例分层且可注入**：四层（性能/兼容/质量/长上下文），其中质量层由 `download_datasets.py` 从 HuggingFace 下载抽取（GSM8K、TruthfulQA），生成统一用例文件 `test_cases/quality.json`。
4. **推理模型适配**：采集 `reasoning_content`、`reasoning_tokens`、`content_ttft_ms`、`cached_tokens`；对推理渠道默认把 max_tokens 抬到 `reasoning_max_tokens`（4096），避免 reasoning 耗尽内容空间（对应旧脚本 REASONING_MAX_TOKENS=4096 的做法）。
5. **结构化输出**：`output/raw/*.json`（全量）+ `output/summary.json`（聚合+评分）+ `output/summary_table.md`（对比表）+ `export_report.py` 生成带公式的 Excel。

## 四、差距清单（新框架仍可补齐的方向）

| 差距项 | 旧脚本有 | 新框架现状 | 说明 |
|---|---|---|---|
| 输出质量「代码生成/指令遵循」并排展示 | ✅ | ⚠️ 部分 | 质量层已有 math/hallucination 判分；代码/指令遵循可再挂 LeetCode/IFEval 等 HF 数据集 |
| 推理指纹（reasoning 相似度对比） | ✅ | ❌ 未覆盖 | 可加 `difflib` 对比两渠道 reasoning 文本相似度，判断是否同源模型 |
| 前缀 cache 命中率对比 | ✅ | ⚠️ 部分 | 已采集 `cached_tokens`，但「相同前缀 + 不同问题」的前缀 cache 专项未单列 |
| 幻觉检测的「虚构知识」反向题 | ✅ | ⚠️ 部分 | TruthfulQA 覆盖正向事实，可补充反向虚构题（如旧脚本的「张伟明诺贝尔奖」） |
| token 开销隐藏 system prompt 注入检测 | ✅ | ❌ 未覆盖 | 旧脚本通过对比 prompt_tokens 差异发现「隐藏 system 注入」，可加 |

> 结论：新框架在「工程化、可复现、可扩展、可输出报告」上全面强于旧脚本；旧脚本在「推理指纹、前缀 cache、隐藏注入检测」等深度诊断项上仍有独特价值，已列入后续补齐清单。
