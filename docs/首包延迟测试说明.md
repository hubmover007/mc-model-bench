# 首包延迟（TTFT）专项测试说明

> 脚本：`probe_ttft.py`（标准库实现，零依赖，不需要 `requests`）
> 定位：只做「首包/首 token/首内容」专项探测；完整能力对比仍用 `runner.py`（20 条用例、四层评分）。
> 默认目标：`easyrouter` 渠道上的 `gemini-3.1-pro-preview`。

---

## 一、为什么「首包」必须拆成三个口径

同一个模型、同一次请求，"首包"可能指三个完全不同的时间点。混用会导致结论互相打架：

| 口径 | 字段 | 时间点 | 回答的问题 |
|---|---|---|---|
| 首字节 | `ttfb_headers_ms` | 请求发出 → HTTP 响应头到达 | 网关受理快不快？要不要换线路/换渠道？ |
| 首 token（业界 TTFT） | `first_token_ms` | 请求发出 → 第一个 delta 到达 | 服务端 prefill/排队快不快？ |
| 首内容（用户可见首字） | `first_content_ms` | 请求发出 → 第一个 `content` 到达 | **用户真正看到文字要等多久？** |

推理模型（`*-preview`、`*-reasoning`）会先吐 `reasoning_content`，再吐 `content`。历史数据里
首 token 与首 content 相差 76 秒的样本真实存在过，所以：

- 只测「首 token」→ 高估体验（用户屏幕还是空的）
- 只测「首 content」→ 把模型能力问题和「思考期长」混为一谈
- **两者都测 + 两者之差 = 思考期耗时**，才能分别定责

另外脚本同时给冷/热两套口径：

- `cold_first_token_ms`：含 DNS + TCP + TLS 建连
- `first_token_ms`：不含建连（长连接复用后的真实服务端耗时）
- 二者之差 ≈ 连接复用能省下的时间

## 二、指标字典

| 字段 | 含义 | 经验参考（公网渠道） |
|---|---|---|
| `dns_ms` | DNS 解析 | < 50ms（命中缓存 < 5ms） |
| `tcp_ms` | TCP 三次握手 | 同城 < 30ms，跨区 30~150ms |
| `tls_ms` | TLS 握手（含证书校验） | 30~200ms；TLS1.3 更快 |
| `connect_ms` | 三段合计 | 同城 < 100ms，跨境 300~800ms |
| `send_ms` | 请求体写入本地 socket | < 5ms |
| `ttfb_headers_ms` | 响应头到达（网关受理） | 100~800ms；> 1s 说明排队/网关慢 |
| `first_sse_ms` | 第一个 `data:` 行 | 通常贴近首 token |
| `first_token_ms` | 首个 delta（可能是 reasoning） | P50 < 2s 优秀，P95 < 5s 可接受 |
| `first_content_ms` | 首个 `content` | 非推理模型 ≈ 首 token；推理模型可能 +数十秒 |
| `reasoning_gap_ms` | 思考期 = 首 content − 首 token | 推理模型的固有成本，产品上要能感知 |
| `e2e_ms` | 到 `[DONE]` 的总生成时间 | 与输出长度相关，配合 `tokens/s` 看 |
| `cold_first_token_ms` | 含建连的首 token | 与热口径差值即建连成本 |
| `total_ms` | 含建连的总耗时 | — |

报告同时给出 **P50 / P90 / P95 / P99 / 均值 / 最小 / 最大 / 抖动（P95−P50）**。
首包是典型长尾指标：**结论只引用 P50 与 P95，不引用均值**。

## 三、用法

```bash
# 0) 看内置用例
python probe_ttft.py --list-cases

# 1) 最常用：EC2 / 本地直接测 easyrouter 上的 gemini-3.1-pro-preview
export EASYROUTER_API_KEY=sk-xxx          # Windows: $env:EASYROUTER_API_KEY="sk-xxx"
python probe_ttft.py --model gemini-3.1-pro-preview --runs 20 --warmup 2

# 2) 短输入 + 长输入（看 prefill 对首包的影响）
python probe_ttft.py --cases short,long --runs 20

# 3) 长连接复用（区分「建连成本」与「服务端耗时」）
python probe_ttft.py --keepalive --runs 20

# 4) 多模型同口径基线对比（必须同一时段、同一连接模式）
python probe_ttft.py --models gemini-3.1-pro-preview,gpt-5.2,kimi-k3 --runs 20

# 5) 规避前缀缓存，测真实冷首包
python probe_ttft.py --fresh-prompt --runs 20

# 6) 观察 gzip 攒包对首包的影响（对照组）
python probe_ttft.py --accept-encoding "gzip, deflate" --runs 10

# 7) 不消耗真实额度的自检（本地 mock）
python mock_server.py 18080
python probe_ttft.py --base-url http://127.0.0.1:18080/v1 --api-key test --runs 5
```

输出（默认 `output_ttft/ttft_<时间戳>/`）：

- `report.md`：配置 + 三口径定义 + 阶段分解表 + 逐次明细 + **自动诊断** + **正反建议**
- `probe.json`：每次采样的完整阶段数据（可二次分析）
- `report.csv`：明细表，可直接贴 Excel

退出码：`0` = 至少一条成功；`2` = 全部失败（便于放进 cron 做定时探测告警）。

## 四、正反建议

### 4.1 「正」面：这个测法能解决什么

1. **定位瓶颈归属**：把 DNS/TCP/TLS/响应头/首 token 拆开，直接回答「慢在网络、慢在网关排队、还是慢在模型 prefill」——三者的处置动作完全不同（换线路 / 换渠道 / 换模型或缩短输入）。
2. **区分「首 token」与「首 content」**：推理模型二者可能差几十秒。单口径测试要么高估体验、要么误判模型。
3. **冷热两套口径**：`cold_first_token_ms − first_token_ms` 就是连接复用的收益，可直接支撑「上 keep-alive / 连接池」的决策。
4. **看分布不看单次**：P50/P95 + 抖动，避免被一次「幸运样本」带偏；首包验收必须用 P95。
5. **暴露缓存与截断污染**：`cached_tokens > 0` 说明命中了前缀缓存（首包虚低）；`finish_reason=length` 说明思考吃掉了输出额度（可能永远等不到 content）。脚本会统计并告警。
6. **零依赖可移植**：纯标准库，EC2 / 容器 / 笔记本直接跑；不引入代理库行为差异。

### 4.2 「反」面：必须写进报告的局限

1. **单点单机，不代表全链路**：测到的是「这台机器 → 该渠道」。跨区、跨运营商、走代理、企业 TLS 中间盒都会显著改变结果，只能作基线参考。
2. **只测首包，不测吞吐**：首包快 ≠ 生成快。必须配合 `tokens/s` 与 `e2e`，否则会出现「首包 300ms 但吐 20 分钟」的误判。
3. **preview 模型本身不稳定**：`*-preview` 通常指向灰度/共享后端，容量与版本随时变化；单日数据不等于长期结论，需连续多天、多时段复测。
4. **渠道差异会被误归因到模型**：同一模型在不同渠道首包可能差 10 倍（历史数据中 glm 在两条渠道上 E2E 差 4.5 倍）。结论必须写成「模型 @ 渠道」。
5. **HTTP/1.1 单连接**：脚本用 `http.client`（HTTP/1.1），测不到 HTTP/2 多路复用 / QUIC 的表现；若生产走 HTTP/2/3，需另用对应客户端补测。
6. **`Accept-Encoding` 会改变首包**：带 gzip 时部分网关会攒包再压，首个 chunk 被推迟。脚本默认 `identity`（最接近真实首字），生产若开 gzip 需单独对照。
7. **小样本会骗人**：`--runs 5` 的 P95 没有统计意义；下结论建议 ≥20 次，且必须剔除预热样本。

### 4.3 落地建议（按优先级）

1. **先定验收口径**：产品说的「首包」通常指**首 content**；技术 SLA 建议同时约定 `first_token_p95 ≤ 3s` 与 `first_content_p95 ≤ 8s`（按业务调整），并写清是否含建连。
2. **采样规范**：每用例 ≥20 次、预热 2 次剔除、跨 2 个时段（闲时/忙时）各一轮；报告只引用 P50/P95。
3. **固定对照基线**：同测一个已知稳定模型（如 `gpt-5.2` / `kimi-k3`）作为「本机 → 本渠道」的网络基线，用差值判断 gemini 是否真的慢。
4. **分输入长度测**：首包对输入长度敏感（prefill），至少跑 `short` 与 `long`，确认随输入 token 的增长斜率正常。
5. **缓存隔离**：测冷首包必须每次换 prompt（`--fresh-prompt`），否则测到的是缓存命中速度。
6. **纳入定时探测**：本脚本可直接进 cron，持续观察 preview 版本变更带来的首包跳变。
7. **不要只看首包做选型**：选型 = 首包(P95) + 生成速度 + 质量得分 + 长上下文，缺一不可。

## 五、常见坑

| 坑 | 现象 | 规避 |
|---|---|---|
| 前缀缓存命中 | 首包异常低（如 200ms），且 `cached_tokens > 0` | `--fresh-prompt`，或按 `cached_tokens` 剔除样本 |
| 思考吃掉输出额度 | 只看到 reasoning，`content` 为空且 `finish_reason=length` | 调大 `--max-tokens`；推理模型另设 `reasoning_max_tokens` |
| gzip 攒包 | 首字节很快，首 chunk 很慢 | `--accept-encoding identity`（默认） |
| 连接未复用 | 冷口径比热口径多出数百 ms | 生产端启用 keep-alive；用 `--keepalive` 对比 |
| 代理叠加 | 建连耗时异常（>1s）且 DNS 很慢 | 先 `--base-url` 直连对照，或在本机排除代理 |
| 429 限流 | 失败率升高、日志出现 `rate_limit` | 降低并发/频率，读 `Retry-After`（脚本已支持自动退避） |
| 单次结论 | 一次 800ms 就当「首包优秀」 | 至少 20 次看 P95 |
