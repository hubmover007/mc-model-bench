# 代码解读：测试内容 / 代码逻辑 / 输出结果

本文解读 mc-model-bench 多渠道统一模型测试框架：测了什么（测试内容）、怎么实现（代码逻辑）、产出什么（输出结果）。

## 一、测试内容（测什么）

目标是「同一模型 × 不同渠道」的服务能力对比。所有渠道共用**同一套参数、同一批用例、相同顺序**，只替换 `base_url / api_key / model`。

### 1.1 四层用例（test_cases/*.json，共 20 条全新 HF 抽样用例）

| 层 | 文件 | 条数 | 数据集来源 / 内容 | 目的与默认权重（建议范围） |
|---|---|---:|---|---|
| 性能基准 | performance.json | 4 | `tatsu-lab/alpaca` + `abisee/cnn_dailymail` 构造「短/长输入 × 短/长输出」完整四象限 | TTFT、内容TTFT、生成速度(tok/s)、E2E、重试总耗时（权重 **0.30**，范围 `0.25~0.35`） |
| 功能兼容 | compatibility.json | 5 | `rajpurkar/squad_v2` 语料驱动：`stream_sse`、`function_calling`（双工具）、`json_mode`、`system_prompt`、`stop_param` | 5 项核心协议契约逐项校验并记录失败详情（权重 **0.20**，范围 `0.15~0.25`） |
| 质量评测 | quality.json | 8 | `openai/gsm8k`(3题，≥4步推理) + `truthfulqa/truthful_qa` MC1(3题) + `cais/mmlu` CS/Logic(2题)，`offset>=35` 跳过旧题 | 程序化精确判分（`gsm8k_exact` / `mc_letter`），区分模型真实推理与抗幻觉能力（权重 **0.30**，范围 `0.25~0.35`） |
| 长上下文 | long_context.json | 3 | 大海捞针 **10K**(depth=0.25) / **64K**(depth=0.75) / **128K**(depth=0.50) | 覆盖首段、后段、中段不同深度的长窗口检索与截断检测（权重 **0.20**，范围 `0.15~0.25`） |

- 性能层覆盖「短输入短输出/短输入长输出/长输入短输出/长输入长输出」4 个象限，兼顾采样代表性与低成本。
- 四层测试集均可通过 `python download_datasets.py --all` 从 HuggingFace 公开 REST API 一键拉取重建，原始行缓存于 `datasets/*.jsonl`。
- 长上下文输出侧单独设大 `max_tokens`（4096，推理模型自动抬到 `reasoning_max_tokens=16384`），避免「思考 token 耗尽输出上限导致误判」。

### 1.2 指标与异常审计（每个用例记录）

- **TTFT**：首 token 延迟（`ttft_ms`，推理模型 = 首个 reasoning 或 content token）、**首个内容 token 延迟**（`content_ttft_ms`，剥离思考时间后的真实开口延迟）
- **端到端延迟** `e2e_ms`（当次成功尝试耗时）、**含重试总挂钟耗时** `total_wall_ms`（从第 1 次尝试到最终完成的总耗时）、**生成耗时** `generation_ms`、**生成速度** `tokens_per_sec`（completion_tokens / 生成耗时）
- **chunk 分布**：`chunk_size` / `chunk_interval_ms`（min/avg/max/std）+ 逐 chunk 时间线
- **usage**：`prompt_tokens` / `completion_tokens` / `total_tokens` / `reasoning_tokens` / `cached_tokens`
- **错误与重试轨迹**：支持 `5xx / timeout / network / 408 / 429(Rate Limit)` 自动退避重试；无论最终成功或失败，均在 `retry_history` 记录每次失败尝试的状态码、错误类型与耗时（`elapsed_ms`），并在汇总报告公开「靠重试成功用例数 (`retried_cases`)」与「总重试次数 (`retry_count`)」，绝不掩盖偶发故障或尾延迟
- **答案通道审计**：当 `content` 为空且 `finish_reason != "length"` 时，判分器自动回退读取 `reasoning` 避免误判，但同时标记 `misplaced_answer=True` 并在报告中单独统计「答案落错通道次数」
- **finish_reason**、内容字符数、推理字符数

## 二、代码逻辑（怎么实现）

### 2.1 模块与数据流

```
download_datasets.py ──(HuggingFace datasets-server)──> datasets/*.jsonl ──> test_cases/quality.json
                                                                                    │
config/providers.json（模板 providers-template.json）────────────────────────────┤
test_cases/{performance,compatibility,long_context}.json ──────────────────────────┤
                                                                                    ▼
                                              runner.py（统一执行器）
                                                                                    │
                                   ┌────────────────────────────────────────────────┤
                                   ▼                  ▼                 ▼           ▼
                          output/raw/*.json   output/order.json  output/summary.json  output/summary_table.md
                                                                                    │
                                                              export_report.py（+ report_template.xlsx）
                                                                                    ▼
                                                                         report_<时间戳>.xlsx
```

### 2.2 关键实现点

**（1）组合展开 `build_combos()` 与统一请求构造 `build_request_body()`**（runner.py）

- 配置里 `channels`（渠道：base_url/api_key）与 `models`（模型：aliases/reasoning/context/supports）**分离**，`build_combos()` 把它们做笛卡尔积展开成「模型@渠道」组合（3 模型 × 2 渠道 = 6 个组合），每个组合等价于一个待测 provider。
- `aliases` 让同一模型在不同渠道用不同调用名；某模型不挂某渠道时（aliases 里没有该渠道）自动跳过。

```python
def build_request_body(provider, case, shared_params, reasoning_max_tokens):
    body = {"model": provider["model"], "messages": build_messages(case)}
    ...
```

- `messages` 由用例统一生成；长输入的 `{filler}` 用 `build_filler(稳定种子)` 生成，种子只依赖「用例ID」，因此**所有渠道收到的 prompt 逐字一致**。
- `temperature`：若模型 `supports.temperature=false`（如 kimi-k3）则不传，除非用例 `force_params=true`（用于专门测「temperature 接受度」）。
- `max_tokens`：推理模型（`reasoning=true`）自动抬到 `reasoning_max_tokens`（默认 4096），除非用例 `force_params=true`（如 max_tokens 约束测试）。

**（2）流式采集 `run_stream()`**

- 逐行解析 SSE：`data:` 行 → `json.loads` → 取 `delta.content`（内容）与 `delta.reasoning_content / delta.reasoning`（推理）分别累计。
- 记录每个内容 chunk 的到达时间与长度 → 计算 chunk 大小/间隔分布。
- 记录 `usage`（流末 chunk）、`finish_reason`、`data: [DONE]` 是否出现。
- 部分渠道 SSE 不带 charset → 回退 `resp.encoding="utf-8"`，避免中文损坏。

**（3）usage 字段统一抽取 `extract_usage_fields()`**

兼容不同渠道字段位置差异：`reasoning_tokens` 可能在 `usage.completion_tokens_details.reasoning_tokens` 或 `usage.reasoning_tokens`；`cached_tokens` 同理。

**（4）质量判分 `judge_answer()` 与通道回退 `pick_answer()`**

- `pick_answer(result)`：优先取 `output.text`（即 `content`）；若 `content` 为空且 `finish_reason != "length"`，自动回退取 `output.reasoning` 并标记 `source="reasoning"`（记入 `misplaced_answers` 统计）；若 `finish_reason == "length"` 则标记 `truncated` 不予给分。
- `gsm8k_exact`：支持 `\boxed{}`、`####`、显式答案短语与末位数字提取，使用 `Decimal` 进行数值等价比较（`$18.00 == 18`）。
- `mc_letter`：针对 TruthfulQA MC1 与 MMLU 选择题，提取模型给出的最终选项字母（`A`~`Z`）进行精确匹配。

**（5）校验 `validate_case()`**：把每个失败项的具体表现写入 `checks[].detail`（如「未返回 tool_calls」「输出非 JSON」「未收到 data: [DONE]」）。

**（6）顺序执行与变量控制**（main 循环）：用例为外层、渠道为内层（case-major），逐条依次发给所有渠道，发送时间戳写入 `order.json`。

**（7）动态实验配置说明 `build_test_config()` 与评分 `compute_scores()`**：
- 报告中的用例设计说明由 `_describe_layer_cases()` 根据当次实际加载的 `test_cases/*.json` 动态生成，彻底避免配置说明与实际执行项不一致。
- 性能得分 = 平均(TTFT 得分, 速度得分, E2E 得分)，TTFT/E2E 越低分越高、速度越高分越高（全渠道最优=100）
- 兼容得分 = 通过数/总数 × 100；质量得分 = 正确数/总数 × 100；长上下文得分 = 检索成功数/实际执行数 × 100（跳过不计分母）
- 总评分 = 性能×0.3 + 兼容×0.2 + 质量×0.3 + 长上下文×0.2（权重可改）

### 2.3 HuggingFace 下载抽取（download_datasets.py）

- 零依赖，使用 datasets-server 公开 REST API（`https://datasets-server.huggingface.co/rows`），分页拉取。
- 支持 `--all` 一键从 HuggingFace 构建全部四层用例：`gsm8k`（`openai/gsm8k`, 多步推理筛选）、`truthfulqa`（`truthfulqa/truthful_qa`, `multiple_choice` MC1 确定性乱序）、`mmlu_cs` / `mmlu_logic`（`cais/mmlu`）、以及基于 `tatsu-lab/alpaca`、`abisee/cnn_dailymail`、`rajpurkar/squad_v2` 的性能四象限与兼容性契约用例。
- 默认带非零 `offset`（`>=35`）避开早期样本，原始数据缓存 `datasets/*.jsonl`。

## 三、输出结果（产出什么）

每次运行结果写入带时间戳的子目录 `output/run_<时间戳>/`（不覆盖历史；`--no-ts` 可直接写到 `--out`），结构如下：

```
output/run_<时间戳>/
├── raw/<layer>/<模型id>__<渠道id>__<用例id>.json   # 全量原始数据
├── order.json                                      # 发送顺序证据
├── summary.json                                    # 聚合 + 评分
└── summary_table.md                                # Markdown 对比表
```


### 3.3 output/summary.json（聚合 + 评分）

各渠道按层聚合：性能（TTFT 均值/P50/P95、速度、E2E、推理 tokens、缓存 tokens）、兼容（按功能点通过/总数）、质量（按类别正确率）、长上下文（各梯度 是/否/跳过）+ 四项得分与总评分。

### 3.4 output/summary_table.md（Markdown 对比表）

测试环境表（hostname/OS/CPU/内存/环境标注）+ 五张对比表：性能基准层、功能兼容层、质量层、长上下文专项、综合评分（见 runner.py `render_markdown`）。

### 3.5 report_<时间戳>.xlsx（Excel 报告，export_report.py 生成）

基础 8 个 sheet：说明 / 汇总表 / 性能明细 / 兼容性明细 / 质量明细 / 长上下文明细 / 评分模型 / 实验配置；
若本次运行启用了缓存专项（`--cache`），额外合并一个 **缓存命中** sheet。
汇总表与评分模型的公式（AVERAGEIFS/COUNTIFS/RANK）自动从明细表取值，替换数据后自动刷新。
未启用缓存专项时，「说明」sheet 与 `summary_table.md` 第 8 节都会显式标注「本次未启用缓存专项」，避免误以为漏跑。

### 3.6 缓存专项（run_cache，--cache / --cache-only）

> 缓存测试**不是默认执行项**：它会给每个「模型×渠道」组合额外发出约 7 次请求
> （长前缀连打 5 次 + 前缀复用 1 次 + 基线 1 次），所以做成显式开关，避免每次全量跑都白付额度。

**执行流程（每个组合）**

1. 构造 2000 token 的确定性长前缀 A、B（`build_filler` + 固定种子），问题 q1/q2；
2. **连打 5 次**同一 prompt（run1 建立缓存、run2~5 测命中），记录每次 `cached_tokens` / `cache_write_tokens`；
3. **前缀复用**：同 session、同前缀 A、换问题 q2，观察是否增量命中；
4. **基线**：独立 session + 不同前缀 B，作为「必然不命中」对照，排除渠道恒定返回缓存字段的假象；
5. **session 探测**：优先带 `session_id` 请求以粘住同一后端节点；若渠道返回 400/422 则自动去掉 `session_id` 重试（`session` 列记「否」）。

**五种缓存类型判定（`classify_cache`）**

| 类型 | 判定特征 | 含义 |
|---|---|---|
| 前缀缓存 | 连打命中 + 前缀复用增量命中 | 真前缀缓存（最理想） |
| 精确匹配缓存(无前缀复用) | 连打命中，但前缀复用不比基线高 | 只缓存完全相同的 prompt |
| 反常(连打miss但前缀命中) | 连打未命中却前缀命中 | 命中逻辑可疑，需复测 |
| 字段不可信 | 基线也返回 `cached_tokens>0`，或数值恒定 | 渠道字段不可信，不能用于结论 |
| 无缓存 | 全程 `cached_tokens` 为 0/缺失 | 该渠道未透传缓存字段（或确实无缓存） |

**产出**：`cache_summary.json` + `cache_table.md`；`--cache` 时合并进 `report.xlsx` 的「缓存命中」sheet；
`--cache-only` 时跳过 20 条常规用例，只生成独立的 `cache_report.xlsx`（单 sheet）与 `cache_table.md`。

**重要预期**：若渠道（如 easyrouter 某些模型）不返回 `prompt_tokens_details.cached_tokens`，
结论会是**「无缓存」或「字段不可信」——这是渠道透传能力的事实，不是脚本 bug**；
要判断模型侧是否支持缓存，需改用直连官方 API 或支持的渠道对比。

**字段兼容**（`extract_usage_fields`）：缓存**读**取所有候选中的最大值（>0 优先，避免网关同时给一个恒 0 的
OpenAI 字段和一个真实的 Anthropic 字段时漏判）：`prompt_tokens_details.cached_tokens` /
`input_tokens_details.cached_tokens` / 顶层 `cached_tokens` / Anthropic `cache_read_input_tokens` /
Gemini `cachedContentTokenCount` / `prompt_cache_hit_tokens`，以及任何名字含 `cache_read|cached_tokens|cache_hit` 的字段。
缓存**写**优先单字段；若网关把 `cache_creation` 拆成 TTL 桶（如 easyrouter 的
`claude_cache_creation_5_m_tokens` + `claude_cache_creation_1_h_tokens`）则求和。
`cache_summary.json` 会**原样保留每次请求的 `usage`**，并给出 `cache_field_seen` / `cache_fields_present`
（渠道到底返回了哪些缓存字段，如 `prompt_tokens_details.cached_tokens`）。

**Anthropic 系必须显式打标记**：Anthropic 的 prompt caching 不是自动的，请求里要在长前缀 content block 上写
`cache_control: {"type": "ephemeral"}` 才会建缓存；纯字符串 prompt 即使连打 5 次也必然 `cached=0`。
因此提供 `--cache-control`：把缓存专项的 prompt 改写成两个 content block（长前缀打断点 + 问题），
用来区分「请求方式没触发缓存」与「渠道不支持缓存」。OpenAI 系是自动前缀缓存，该字段一般被忽略，可安全用于对照。
若网关拒绝 content block（400/422），脚本会自动降级为纯文本重试，并记 `cache_control_supported=false`。

**判定为「无缓存」时的排查顺序**：①看 `cache_field_seen` 是否「未透传」→ 换直连/换渠道；
②透传但恒 0 → 加 `--cache-control` 重测；③打了标记仍恒 0 → 渠道确未实现；
④用支持自动缓存的模型（OpenAI 系）做阳性对照，确认测试链路本身正常。

## 四、快速运行

```bash
pip install -r requirements.txt

# 1. 配置渠道 + 模型（只改 base_url/api_key/model），并 export 各渠道 api key
export EASYROUTER_API_KEY=sk-...   # Windows: $env:EASYROUTER_API_KEY="sk-..."
export MAYI_API_KEY=sk-...

# 2. （可选）从 HuggingFace 下载抽取质量层用例
python download_datasets.py --datasets gsm8k,truthfulqa --limit 50

# 3. 预检 / 执行（--env-tag 标注测试环境并写入报告，本地/EC2 各跑一次可区分）
python runner.py --sample --env-tag "本地笔记本"    # 示例模式：复用性能层第1条，每个组合只跑1次（6次）
python runner.py --list-cases
python runner.py --list-models                      # 列出「模型@渠道」组合（--models/--channels 用的是这里的 id）
python runner.py --dry-run
python runner.py --once --env-tag "本地笔记本"      # 单次模式：全量用例每条只跑 1 次、不重试
python runner.py --env-tag "EC2 g5.xlarge"          # 全部组合 × 全部用例（EC2 上跑）

# 3.1 缓存命中专项（可选，默认不跑；report.xlsx 才会出现「缓存命中」sheet）
python runner.py --env-tag "EC2" --cache            # 先跑缓存，再跑常规用例，合并进同一份报告
python runner.py --cache-only                        # 只跑缓存（约 7 次请求/组合），出 cache_report.xlsx

# 4. 生成本地 mock 自检（无需真实 key）
python mock_server.py 18080
python runner.py --sample --providers-file config/providers.mock.json --out output_mock
python runner.py --providers-file config/providers.mock.json --out output_mock

# 5. 生成 Excel 报告
python gen_report_template.py                      # 生成报告模板
python export_report.py --out output --result 测试报告.xlsx
```
