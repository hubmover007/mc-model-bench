# 代码解读：测试内容 / 代码逻辑 / 输出结果

本文解读 mc-model-bench 多渠道统一模型测试框架：测了什么（测试内容）、怎么实现（代码逻辑）、产出什么（输出结果）。

## 一、测试内容（测什么）

目标是「同一模型 × 不同渠道」的服务能力对比。所有渠道共用**同一套参数、同一批用例、相同顺序**，只替换 `base_url / api_key / model`。

### 1.1 四层用例（test_cases/*.json）

| 层 | 文件 | 条数 | 内容 | 目的 |
|---|---|---|---|---|
| 性能基准 | performance.json | 12 | 短/长输入 × 短/长输出 四象限 | TTFT、生成速度、端到端延迟、chunk 分布 |
| 功能兼容 | compatibility.json | 11 | SSE 格式、stop、max_tokens、temperature 接受度、temperature=0 一致性、Function Calling、JSON mode、多轮、system 提示词 | 每个失败项记录具体表现 |
| 质量 | quality.json | 6（样例） | GSM8K 数学推理 + TruthfulQA 幻觉/事实性 | 判分正确率，数据来自 HuggingFace |
| 长上下文 | long_context.json | 4 | 大海捞针 10K/32K/64K/128K | 检索能力，按渠道标称上下文自动跳过 |

- 性能层「短输入短输出/短输入长输出/长输入短输出/长输入长输出」各 3 条，覆盖不同 token 量级。
- 质量层的 `quality.json` 由 `download_datasets.py` 从 HuggingFace 下载抽取生成（仓库自带 6 条兜底样例）。
- 长上下文输出侧单独设大 `max_tokens`（2048，推理模型自动抬到 4096），避免「输出上限耗尽导致误判」。

### 1.2 指标（每个用例记录）

- **TTFT**：首 token 延迟（`ttft_ms`，推理模型 = 首个 reasoning 或 content token）、首个内容 token 延迟（`content_ttft_ms`）
- **端到端延迟** `e2e_ms`、**生成耗时** `generation_ms`、**生成速度** `tokens_per_sec`（completion_tokens / 生成耗时）
- **chunk 分布**：`chunk_size` / `chunk_interval_ms`（min/avg/max/std）+ 逐 chunk 时间线
- **usage**：`prompt_tokens` / `completion_tokens` / `total_tokens` / `reasoning_tokens` / `cached_tokens`
- **错误**：类型（timeout/network/http_error/bad_json/api_error）、状态码、每次重试记录
- **finish_reason**、内容字符数、推理字符数

## 二、代码逻辑（怎么实现）

### 2.1 模块与数据流

```
download_datasets.py ──(HuggingFace datasets-server)──> datasets/*.jsonl ──> test_cases/quality.json
                                                                                    │
config/providers.json ─────────────────────────────────────────────────────────────┤
test_cases/{performance,compatibility,long_context}.json ──────────────────────────┤
                                                                                    ▼
                                              runner.py（统一执行器）
                                                                                    │
                                   ┌────────────────────────────────────────────────┤
                                   ▼                  ▼                 ▼           ▼
                          output/raw/*.json   output/order.json  output/summary.json  output/summary_table.md
                                                                                    │
                                                              export_report.py（+ report_template.xlsx）
                                                                                    ▼
                                                                         report_<时间戳>.xlsx
```

### 2.2 关键实现点

**（1）组合展开 `build_combos()` 与统一请求构造 `build_request_body()`**（runner.py）

- 配置里 `channels`（渠道：base_url/api_key）与 `models`（模型：aliases/reasoning/context/supports）**分离**，`build_combos()` 把它们做笛卡尔积展开成「模型@渠道」组合（3 模型 × 2 渠道 = 6 个组合），每个组合等价于一个待测 provider。
- `aliases` 让同一模型在不同渠道用不同调用名；某模型不挂某渠道时（aliases 里没有该渠道）自动跳过。

```python
def build_request_body(provider, case, shared_params, reasoning_max_tokens):
    body = {"model": provider["model"], "messages": build_messages(case)}
    ...
```

- `messages` 由用例统一生成；长输入的 `{filler}` 用 `build_filler(稳定种子)` 生成，种子只依赖「用例ID」，因此**所有渠道收到的 prompt 逐字一致**。
- `temperature`：若模型 `supports.temperature=false`（如 kimi-k3）则不传，除非用例 `force_params=true`（用于专门测「temperature 接受度」）。
- `max_tokens`：推理模型（`reasoning=true`）自动抬到 `reasoning_max_tokens`（默认 4096），除非用例 `force_params=true`（如 max_tokens 约束测试）。

**（2）流式采集 `run_stream()`**

- 逐行解析 SSE：`data:` 行 → `json.loads` → 取 `delta.content`（内容）与 `delta.reasoning_content / delta.reasoning`（推理）分别累计。
- 记录每个内容 chunk 的到达时间与长度 → 计算 chunk 大小/间隔分布。
- 记录 `usage`（流末 chunk）、`finish_reason`、`data: [DONE]` 是否出现。
- 部分渠道 SSE 不带 charset → 回退 `resp.encoding="utf-8"`，避免中文损坏。

**（3）usage 字段统一抽取 `extract_usage_fields()`**

兼容不同渠道字段位置差异：`reasoning_tokens` 可能在 `usage.completion_tokens_details.reasoning_tokens` 或 `usage.reasoning_tokens`；`cached_tokens` 同理。

**（4）质量判分 `judge_answer()`**

- `gsm8k_exact`：取模型输出末位数字，与参考数字数值比对（GSM8K 答案在 `answer` 的 `#### ` 之后）。
- `truthfulqa_any`：标准答案列表任一条命中输出（归一化后子串匹配）。

**（5）校验 `validate_case()`**：把每个失败项的具体表现写入 `checks[].detail`（如「未返回 tool_calls」「输出非 JSON」「未收到 data: [DONE]」）。

**（6）顺序执行与变量控制**（main 循环）：用例为外层、渠道为内层（case-major），逐条依次发给所有渠道，发送时间戳写入 `order.json`。

**（7）评分**（`compute_scores`，与 Excel 公式一致）：
- 性能得分 = 平均(TTFT 得分, 速度得分, E2E 得分)，TTFT/E2E 越低分越高、速度越高分越高（全渠道最优=100）
- 兼容得分 = 通过数/总数 × 100；质量得分 = 正确数/总数 × 100；长上下文得分 = 检索成功数/实际执行数 × 100（跳过不计分母）
- 总评分 = 性能×0.3 + 兼容×0.3 + 质量×0.2 + 长上下文×0.2（权重可改）

### 2.3 HuggingFace 下载抽取（download_datasets.py）

- 零依赖，使用 datasets-server 公开 REST API（`https://datasets-server.huggingface.co/rows`），分页（每页 100 行）拉取。
- 内置规格：`gsm8k`（openai/gsm8k, split=test）→ `judge=gsm8k_exact`；`truthfulqa`（truthfulqa/truthful_qa, config=generation, split=validation）→ `judge=truthfulqa_any`。
- 抽取结果按统一用例格式写 `test_cases/quality.json`，原始数据缓存 `datasets/<name>.jsonl`。

### 3.2 output/order.json（发送顺序证据）

```json
{"started_at":"...","finished_at":"...","order":[{"order":1,"case_id":"perf_sis_01","provider_id":"easyrouter","sent_at":"..."}]}
```

### 3.3 output/summary.json（聚合 + 评分）

各渠道按层聚合：性能（TTFT 均值/P50/P95、速度、E2E、推理 tokens、缓存 tokens）、兼容（按功能点通过/总数）、质量（按类别正确率）、长上下文（各梯度 是/否/跳过）+ 四项得分与总评分。

### 3.4 output/summary_table.md（Markdown 对比表）

五张表：性能基准层、功能兼容层、质量层、长上下文专项、综合评分（见 runner.py `render_markdown`）。

### 3.5 report_<时间戳>.xlsx（Excel 报告，export_report.py 生成）

7 个 sheet：说明 / 汇总表 / 性能明细 / 兼容性明细 / 质量明细 / 长上下文明细 / 评分模型。
汇总表与评分模型的公式（AVERAGEIFS/COUNTIFS/RANK）自动从明细表取值，替换数据后自动刷新。

## 四、快速运行

```bash
pip install -r requirements.txt

# 1. 配置渠道 + 模型（只改 base_url/api_key/model），并 export 各渠道 api key
export CHANNEL_A_API_KEY=sk-...   # Windows: $env:CHANNEL_A_API_KEY="sk-..."
export CHANNEL_B_API_KEY=sk-...

# 2. （可选）从 HuggingFace 下载抽取质量层用例
python download_datasets.py --datasets gsm8k,truthfulqa --limit 50

# 3. 预检 / 执行
python runner.py --sample          # 示例模式：每个「模型×渠道」组合只跑 1 条示例（3模型×2渠道=6次）
python runner.py --list-cases
python runner.py --dry-run
python runner.py --once            # 单次模式：全量用例每条只跑 1 次、不重试，快速看一轮
python runner.py                   # 全部组合 × 全部用例

# 4. 生成本地 mock 自检（无需真实 key）
python mock_server.py 18080
python runner.py --sample --providers-file config/providers.mock.json --out output_mock
python runner.py --providers-file config/providers.mock.json --out output_mock

# 5. 生成 Excel 报告
python gen_report_template.py                      # 生成报告模板
python export_report.py --out output --result 测试报告.xlsx
```
